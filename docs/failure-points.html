Things that went wrong

Every failure mode we hit,
so you don't have to.

Twenty notebooks. Roughly forty runs that broke. This is the greatest hits: the training curves that went horribly wrong, why they went wrong, and how to fix them without a therapist. Also a quiz at the bottom, because misery loves company.

Filter by severity:
Loss goes to NaN in the first 10 steps
The training curve is a cliff. A very sad cliff.
High +

Symptom

Loss displays a normal number for 1-3 steps, then nan, and stays nan. Model weights are now unusable.

Cause

Learning rate too large for the model + optimizer combination. Gradient explosion at the first optimizer step. Sometimes: numerical instability from mixed precision on a layer that doesn't like it.

Fix

Drop the learning rate by 10×. If you were at 2e-3, try 2e-4. If you were at 2e-4, try 2e-5. Add warmup_ratio=0.03 to your training args. If it still happens, switch from fp16 to bf16 (Ampere+ GPUs only) or force fp32.

Model produces garbage tokens after training
Loss looked fine. Generations are nonsense. What.
High +

Symptom

Training loss decreased normally. Model checkpoint saved. When you call model.generate(), output is repeating tokens, random symbols, or complete nonsense.

Cause (this one bit us three times)

SFTTrainer and DPOTrainer enable gradient checkpointing during training. It stays enabled after trainer.train() exits. Transformers detects it and forces use_cache=False. Every token generation runs the full forward pass without cached keys/values. On a stateful model, this produces garbage.

Fix

# Do this immediately after every trainer.train() call
model.gradient_checkpointing_disable()
model.config.use_cache = True
model.eval()
Model refuses to answer anything after fine-tuning
Every prompt returns “As an AI, I cannot...”.
High +

Symptom

The fine-tune completed. Now every generation, regardless of prompt, is a variant of “I'm sorry, I can't help with that”.

Cause

Two candidates: (1) chat template mismatch — you trained without the model's expected template and now the model treats every prompt as adversarial. (2) The training data disproportionately contained refusal examples and the model overfit on refusal.

Fix

Use tokenizer.apply_chat_template([...]) for both training and inference. If you're on an instruct model (SmolLM2-Instruct, Qwen-Instruct, etc.), this is not optional. Also check the ratio of refusals in your training data.

Loss plateaus immediately and never drops
First epoch loss = last epoch loss. The line is flat.
Medium +

Symptom

Loss oscillates around a fixed value from step 1 to step N. No improvement across epochs.

Cause

Learning rate is too small (rare), OR — and this is more common — the model is not actually receiving gradients. If you're using PEFT, check that get_peft_model() is being called before the trainer wraps it, and that some parameters have requires_grad=True.

Fix

trainable = sum(p.numel() for p in model.parameters() if p.requires_grad)
total     = sum(p.numel() for p in model.parameters())
print(f"Trainable: {trainable:,} / {total:,}")
# For LoRA r=8 on SmolLM2-135M: should be ~460K
# If this prints 0: PEFT config didn't attach properly.
CUDA out of memory during backward pass
Forward pass worked. Backward pass exploded.
Medium +

Symptom

torch.cuda.OutOfMemoryError during the first optimizer step. Forward pass fit; storing activations for backward did not.

Cause

Peak memory during training is roughly: weights + gradients + optimizer state + activations. Adam optimizer alone doubles the memory of the weights. Activations scale with batch size × sequence length.

Fix (try in this order)

1. Reduce per_device_train_batch_size to 1 and use gradient_accumulation_steps=8. Same effective batch size, less peak memory.
2. Enable gradient_checkpointing=True. Trades ~20% speed for ~40% memory.
3. Reduce max_length. Activations scale quadratically with sequence length via attention.
4. Switch from full FT to LoRA. Switch from LoRA to QLoRA. Escalate as needed.

Model overfits to training examples verbatim
On held-out data: nonsense. On training data: perfect.
Medium +

Symptom

Train loss goes below 0.1. Eval loss doesn't. The model can recite training examples word-for-word but fails on paraphrased or held-out inputs.

Cause

Too many epochs on too little data with too much model capacity. Standard overfitting.

Fix

Cut epochs to 3-5. Add validation split and early stopping. Increase lora_dropout from 0.05 to 0.1. If dataset is under 100 examples, consider prompt tuning instead (fewer trainable parameters, less capacity to overfit).

DPO loss stays close to 0.693 and never drops
DPO trained “successfully”. Model has no opinions.
Medium +

Symptom

DPO loss hovers around log 2 ≈ 0.693 for the entire training run. Chosen and rejected responses have the same likelihood after training.

Cause

Chosen and rejected are too similar — the model can't tell them apart. Or beta is too high (KL penalty too strong, policy can't drift from reference).

Fix

Verify your preference pairs by manually eyeballing 10 of them. Chosen should be visibly better. Then drop beta from 0.1 to 0.05. If loss still won't drop, your pairs may need more contrast.

SFTConfig throws “unexpected keyword max_seq_length”
Code worked in every tutorial you found online.
Low +

Symptom

TypeError: SFTConfig.__init__() got an unexpected keyword argument 'max_seq_length'

Cause

trl 1.9.x renamed max_seq_length to max_length. Every StackOverflow answer and old tutorial uses the old name.

Fix

# OLD (trl <= 1.8)
sft_config = SFTConfig(max_seq_length=384, ...)
# NEW (trl >= 1.9)
sft_config = SFTConfig(max_length=384, ...)
DPOConfig throws “unexpected keyword max_prompt_length”
The very same trl migration, just twice.
Low +

Cause

Same trl 1.9.x cleanup. max_prompt_length was removed. The trainer now uses max_length and derives prompt length automatically.

Fix

Just drop the max_prompt_length parameter. Set max_length large enough to fit prompt + longest expected response.

Training is inexplicably slow on Apple Silicon
M4 Max should not take 90 minutes for 20 steps.
Low +

Cause

You're running on CPU because MPS wasn't detected, OR your model is loaded in fp32 when fp16 would run 2-3× faster on MPS, OR your batch size is 1 with sequence length 2048.

Fix

Print torch.backends.mps.is_available(). If False, upgrade PyTorch. If True but you're still slow, load the model with dtype=torch.float16 and move to MPS. See Apple Silicon guide for the full performance sweep.
